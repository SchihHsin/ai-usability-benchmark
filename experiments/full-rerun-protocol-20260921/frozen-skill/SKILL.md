# 实验版开发者知识可用性评测

使用references/rules.md作为唯一评分规则；references/recording.md为过程结构；references/budget-control.md为预算接入。旧计算脚本仅作日志兼容依赖，不用于新评分。

每次只做一个任务的一侧生态，不看旧结论、别的运行或别的生态答案。协议预先规定任务要求、预算、模型和工具。无证据不补造，无需为得到一致结论改变评分。

工具调用前完整输出<prior_answer>，说明仅凭已有知识给出的具体回答和不确定处。然后执行真实搜索、获取，保存全部结果原始顺序与URL、查询改写、正文返回形态、失败和恢复。每次获取先明确目标文档或章节，不因结果不完整而事后缩小范围。

在<answer>中输出完整最终答案，保留命令、代码、参数、来源和未核实处，并用<stop_reason>记录停止原因。执行模型不自报正式分数，不伪造运行通过。

调度器保存process.jsonl和evaluation.json。后评引用实际事件及原文位置；计数由日志计算。M7依据检索前回答，M9/M10依据最终回答，来源文字不代替最终答案。M11输入未有据确定则保留null。不得用模型自信替代内容正确性或运行结果。

## 获取事实与原因分开

对返回只报告可观察状态：错误、标题/导航、摘要/摘录、直接正文、明确截断。不得仅因没有正文就归因于SPA、robots或动态渲染；原因必须另列支持证据，否则写“原因未确定”。未执行代码只能写“未运行”，不能推断无GPU或无权限。

读取前指明目标为完整文档还是具体章节。读取请求要求保留原文结构、代码、正文起止及工具暴露的截断信息；工具不能提供时记未知，不要求工具猜测是否完整。只有需要整页/完整章节且有可核对起止依据，才能给M2=5。任务所需内容齐全不等于原文完整。模型自称“完整取得”不能作为评分依据。

## 执行与后评责任

客户端是唯一过程日志来源。执行模型只输出检索前答案、任务最终答案与停止原因，不手写process/evaluation、哈希、工具计数或证据ID。没有文件工具不等于调度器没有保存记录。

执行后必须按references/post-evaluation.md逐项评价；只运行日志校验和M8计数不算完成评分。M11由scripts/overall_score.py计算百分制，不划等级。结果必须说明每个输入项是已评分、尚未评价、证据不足、不适用还是实测受阻，不得笼统写“未核验齐全”。

执行前和后评必须读取[执行检查](references/execution-checks.md)，并使用任务包的applicability。后评必须通过批次assessment_gate.py；冻结旧实验不回写。
