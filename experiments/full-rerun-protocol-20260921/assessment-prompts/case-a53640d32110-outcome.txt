应用中对全局（global）、局部（local）和共享（shared）内存的越界和未对齐访问；可检测设备硬件报告的错误信息；可检测并报告应用中的内存泄漏。\n\n### 3.2 可检测的错误类型（Table 7）\n\n| 错误名称 | 描述 | 位置 | 精度 |\n|---|---|---|---|\n| **Memory access error** | 全局、局部、共享或全局原子访问的越界或未对齐访问 | Device | 精确（Precise） |\n| **Hardware exception** | 硬件错误报告机制报告的错误 | Device | 不精确（Imprecise） |\n| **Malloc/Free errors** | CUDA kernel 中错误使用 `malloc()/free()` | Device | 精确 |\n| **CUDA API errors** | 应用中 CUDA API 调用返回失败 | Host | 精确 |\n| **cudaMalloc memory leaks** | 使用 `cudaMalloc()` 分配但未释放的设备内存 | Host | 精确 |\n| **Device Heap Memory Leaks** | 设备代码中用 `malloc()` 分配但未释放的内存 | Device | 不精确 |\n\n**精度说明**：\n- **精确错误**：工具可唯一标识并收集全部信息——报告出错线程的 block/thread 坐标、执行访问指令的 PC、访问地址及其大小和类型；若有行号信息还会打印源文件和行号\n- **不精确错误**：由硬件错误报告机制报告，无法精确归属到特定线程，很多情况下无法回溯到源文件和行\n\n### 3.3 使用方法\nMemcheck 是**默认启用**的工具，也可用 `--tool memcheck` 显式启用。默认查找精确、不精确、malloc/free 和 CUDA API 错误；**设备泄漏报告必须显式启用**（`--leak-check full`）。错误在应用执行完毕后显示。\n\n### 3.4 错误报告解读（Understanding Memcheck Errors）\n\n**1）内存访问错误示例**：\n\n```\n========= Invalid __global__ write of size 4 bytes\n=========     at unaligned_kernel():0x160 in memcheck_demo.cu:6\n=========     by thread (0,0,0) in block (0,0,0)\n=========     Address 0x7f6510c00001 is misaligned\n```\n\n- 第 1 行：内存段（`__global__`/`__shared__`/`__local__`）、访问类型（read/write）、访问大小（字节）\n- 第 2 行：kernel 名、指令偏移、源文件和行号（如可用）\n- 第 3 行：出错线程的 thread/block 索引\n- 第 4 行：访问的内存地址和错误类型（out of bounds 或 misaligned）\n\n**2）Malloc/Free 错误示例**：\n\n```\n========= Malloc/Free error encountered : Double free\n```\n\n错误类型包括：\n- **Double free**：对已释放的分配再次调用 `free()`\n- **Invalid pointer to free**：对非 `malloc()` 返回的指针调用 `free()`\n- **Heap corruption**：堆损坏或以意外方式修改堆状态\n\n**3）泄漏错误示例**：\n\n```\n========= Leaked 64 bytes at 0x400200200\n========= Leaked 16 bytes at 0x4012ffff6 on the device heap\n```\n\n在 context 销毁（程序退出、`cudaDeviceReset()`、`cuCtxDestroy()`）时报告未释放的 cudaMalloc 分配和设备堆分配。\n\n**4）CUDA API 错误示例**：\n\n```\n========= Program hit invalid copy direction for memcpy (error 21) on CUDA API call to cudaMemcpy.\n```\n\n包含 API 调用返回值和 API 函数名。\n\n### 3.5 CUDA API 错误检查\n- 支持 CUDA runtime 和 driver API；非零返回值即打印错误消息\n- API 错误报告**不会终止应用**，仅提供额外信息\n\n**报告模式**（`--report-api-errors`）：\n- **all**：报告所有 CUDA API 错误（含 runtime 隐式调用、内部日志捕获的扩展错误、用户显式调用）\n- **extended**（默认）：用户显式调用 + 内部 CUDA 错误日志捕获的扩展错误（类似 `CUDA_LOG_FILE` 行为）\n- **explicit**：仅用户显式调用\n- **no**：禁用\n\n**不报告的错误**（常用于轮询/状态检查）：\n- `cudaErrorNotReady`（`cudaEventQuery`、`cudaStreamQuery`）\n- `cudaErrorPeerAccessAlreadyEnabled`（`cudaDeviceEnablePeerAccess`）\n- `cudaErrorPeerAccessNotEnabled`（`cudaDeviceDisablePeerAccess`）\n\n### 3.6 设备端分配检查\n- 检查 kernel 内 `malloc()` 创建的设备堆分配，默认隐式启用，可用 `--check-device-heap no` 禁用\n- 报告重复 free、非法指针 free；`malloc()` 失败默认报警告（可用 `--report-device-side-allocation-failure no` 禁用）\n- 注意查看设备端回溯以定位 `malloc()/free()` 调用位置\n\n### 3.7 泄漏检查（Leak Checking）\n需指定 `--leak-check full` 启用。跟踪通过 CUDA driver 或 runtime API 创建的设备内存分配。\n\n### 3.8 填充（Padding）\n- 问题：全局内存缓冲区可能在虚拟地址空间中背靠背分配，第一个缓冲区的溢出访问会落在第二个缓冲区中而未被检测为越界\n- `--padding {number}` 自动扩展分配大小，在每个分配后创建填充缓冲区，对填充区域的访问始终视为非法\n- 支持 `cudaMalloc` API、`cudaHostAlloc`、`cudaMallocHost`\n- **不支持** `cudaHostRegister` 或 CUDA 虚拟内存管理 API\n- 注意：会增加设备内存压力，可能导致额外的 CUDA 内存不足错误\n\n### 3.9 流序竞争检测（Stream-ordered race detection）\n用 `--track-stream-ordered-races all` 检测流序分配竞争，报告超出生命周期的流序分配访问。两类竞争：\n- **Use-before-alloc**（`use-before-alloc`）：分配在被使用前不可用——`cudaMallocAsync` 在流上创建的分配不能在没有先验同步事件的情况下在另一流上使用；也包括分配在可用前被 `cudaFreeAsync` 释放\n- **Use-after-free**（`use-after-free`）：释放后使用——`cudaFreeAsync` 在流上释放的分配不能在没有后续同步事件的情况下在另一流上使用\n\n### 3.10 Tensor Core MMA guardrails\n在 Blackwell GPU 上，使用 PTX 第 5 代 Tensor Core 指令族（`tcgen05.*`）时，可用 PTXAS 标志 `-g-tmem-access-check` 让汇编器在 TCMMA 指令周围插入 guardrails。在 memcheck 下运行此类程序可报告非法 TCMMA 操作（如 tensor memory 的越界/未对齐访问、relinquish 调用后的分配）。示例报告：\n\n```\n========= Tensor Memory column 32 being accessed by instruction tcgen05.ld is not allocated. Columns allocated are: 0-31.\n```\n\n---\n\n## 四、Racecheck 工具\n\n### 4.1 功能定义\n运行时共享内存数据访问冒险检测器，主要用于识别使用共享内存（`__shared__`）的 CUDA 应用中的内存访问竞争条件。当前**仅支持检测片上共享内存访问**。\n\n### 4.2 什么是冒险（Hazards）\n两个线程访问同一内存位置导致基于访问相对顺序的非确定性行为。竞争条件表现为间歇性应用故障，或在不同 GPU 上运行时故障。三种典型冒险：\n\n- **WAW（Write-After-Write）**：两线程写同一位置，结果值取决于两访问的相对顺序\n- **WAR（Write-After-Read）**：一个读一个写，写线程排在读线程之前，读线程未读到原始值\n- **RAW（Read-After-Write）**：一个读一个写，读线程在写线程提交前读取了值\n\n### 4.3 使用方法\n\n```bash\ncompute-sanitizer --tool racecheck [sanitizer_options] app_name [app_options]\n```\n\n消除建议：\n- WAW：修改程序使同一位置不发生多重写入\n- RAW/WAR：使读写位置确定性排序，CUDA kernel 中可在两次访问间插入 `__syncthreads()`；warp 内线程间竞争可用 `__syncwarp()`\n\n> ⚠️ 注意：racecheck **不执行任何内存访问错误检查**，建议先运行 memcheck 确保应用无错误。\n\n### 4.4 报告模式（`--racecheck-report`）\n- **Hazard reports（冒险报告）**：单个冒险的详细信息，字节级精确，表示影响该共享内存字节的两线程冲突访问\n- **Analysis reports（分析报告）**（默认）：事后分析报告集，通过分析多个冒险报告和检查设备状态生成\n\n### 4.5 分析报告解读\n示例：\n\n```\n========= WARNING: Race reported between Write access at RAW()+0xf0 in raceGroupBasic.cu:40\n=========     and Read access at RAW()+0x280 in raceGroupBasic:46 [4 hazards]\n```\n\n- 首个词为严重级别（此例 WARNING）\n- 包含访问类型（Read/Write）、kernel 名与偏移、文件名行号（如有）、参与竞争的其他位置、该竞争的 hazard 数量\n- 每份分析报告至少包含一行写访问\n\n### 4.6 冒险报告解读\n示例：\n\n```\n========= ERROR: Potential WAW hazard detected at __shared__ 0x0 in block (0,0,0) :\n=========     Write Thread (0,0,0) at WAW()+0x2f0 in raceWAW.cu:20\n=========     Write Thread (1,0,0) at WAW()+0x2f0 in raceWAW.cu:20\n=========     Current Value : 1, Incoming Value : 2\n```\n\n- 第 1 行：严重级别、冒险类型（WAW/WAR/RAW）、共享内存地址（字节级精确）、block 索引\n- 第 2、3 行：两个竞争线程的详细信息（按时间顺序排列：先发生的在前）\n- 第 4 行（部分类型有）：WAW 或 WAR 时显示 Current Value（第一线程写入后的值）和 Incoming Value（第二线程将写入的值）\n\n### 4.7 严重级别（Severity Levels）\n默认只显示 WARNING 和 ERROR 级别，可用 `--print-level` 设置最低报告级别：\n\n- **INFO**：最低级别，对程序执行无影响的 hazard，仍建议消除\n- **WARNING**：编程模型冒险，但可能是程序员有意为之（如基于线程成组推进假设的 warp 级编程）；初学者遇到应视为冒险源\n- **ERROR**：最高级别，极可能导致数据访问竞争，务必检查\n\n> ⚠️ 重要提示：在现代 GPU 架构上，不能无条件假设 warp 内线程锁步执行（该假设仅适用于 Volta 之前的 Kepler/Maxwell/Pascal）。从旧架构移植应用时必须修复无显式同步的 warp 同步编程警告，可使用 `__syncwarp()` 内建函数或 Cooperative Groups API。\n\n### 4.8 其他 Racecheck 能力\n- **`cuda::barrier` 支持**：Ampere 及更新 GPU。若编译器少报 barrier 数量，会警告 \"Detected overflow of tracked cuda::barrier structures\"，可用 `--num-cuda-barriers` 解决\n- **异步拷贝支持**：支持 compute capability 8.0 引入的全局到共享内存异步拷贝（`cuda::memcpy_async` / PTX `cp.async`）竞争检测，可检测在必需的 commit/wait 前访问异步拷贝目标的情况（hazard 报告带 `(invalid memcpy_async synchronization)` 标记）；可用 `--racecheck-memcpy-async no` 禁用\n- **Cluster 进入/退出竞争检测**：检测无适当 cluster 范围同步的远程共享内存访问：\n  1. **Late entry race**：目标 block 尚未进入时访问其共享内存（报告 \"Address ... is located in a block that might not have entered yet\"）\n  2. **Early exit race**：目标 block 退出前无适当同步即访问（报告 \"might have already exited\"）\n- **同步跟踪**：`--racecheck-trace-sync yes` 记录同步操作日志（自动设置级别为 INFO），支持 `syncwarp`、`barrier`、`cuda::barrier`、`cluster barrier`、`asynchronous bulk copy`。`syncwarp` 还会打印每个线程的掩码，便于调试掩码错误或线程缺失导致的挂起\n- **死锁检测**：`--racecheck-deadlock-timeout n`（毫秒，默认 0=禁用；过小值可能误报），当前支持 `cuda::barriers` 死锁；配合 `--racecheck-continue-on-deadlock no` 可在死锁时终止应用\n\n---\n\n## 五、Initcheck 工具\n\n### 5.1 功能定义\n运行时未初始化设备内存访问检测器，可识别未经设备端写入或 CUDA memcpy/memset API 初始化即被访问的设备内存。\n\n### 5.2 使用方法\n\n```bash\ncompute-sanitizer --tool initcheck [sanitizer_options] app_name [app_options]\n```\n\n> ⚠️ 注意：initcheck **不执行任何内存访问错误检查**，建议先运行 memcheck。\n\n### 5.3 地址空间选择\n- 默认只检查设备**全局内存**的未初始化访问\n- `--initcheck-address-space shared`：改查共享内存\n- `--initcheck-address-space all`：两种地址空间都查\n\n共享内存未初始化读取报告示例：\n\n```\n========= Uninitialized __shared__ memory read of size 4 bytes\n=========     at KernelSharedError()+0x1a0 in uninitialized_shared.cu:7\n=========     by thread (0,0,0) in block (0,0,0)\n=========     Address 0x0\n```\n\n### 5.4 未使用内存检测\n用 `--track-unused-memory` 启用。报告示例：\n\n```\n=========  Unused __shared__ memory in allocation of size 100 bytes in block (0,0,0)\n=========     Not written 80 bytes at offset 0x14 (0x14)\n=========     These unused bytes represent 80% of the shared memory.\n```\n\n报告包含分配地址和大小、未使用字节数及位置（不连续时为范围）。调节选项：\n- `--unused-memory-threshold`：报告的最低百分比阈值（如设为 81 以上可抑制上面示例）\n- `--unused-shared-memory-report-limit`：每次 launch 的未使用共享内存报告上限，默认 32\n\n> ⚠️ 注意填充（padding）：分配大小可能大于 kernel 中指定的大小，可能导致无法据以行动的未使用内存报告。\n\n---\n\n## 六、Synccheck 工具\n\n### 6.1 功能定义\n运行时工具，识别 CUDA 应用是否正确使用同步原语，特别是 `__syncthreads()` 和 `__syncwarp()` 内建函数及其 Cooperative Groups API 对应物。\n\n### 6.2 使用方法\n\n```bash\ncompute-sanitizer --tool synccheck [sanitizer_options] app_name [app_options]\n```\n\n> ⚠️ 注意：synccheck **不执行任何内存访问错误检查**，建议先运行 memcheck。\n\n### 6.3 报告解读\n每个违规生成一份报告，标识违规源位置和分类。示例：\n\n```\n========= Barrier error detected. Divergent thread(s) in warp\n=========     at ThreadDivergence(int *, int)+0xf0 in divergence.cu:79\n=========     by thread (37,0,0) in block (0,0,0)\n```\n\n报告以 \"Barrier error detected.\" 开头，后接错误分类：\n\n- **Divergent thread(s) in block**：对当前架构上不支持发散的 barrier，检测到 block 内线程发散（如在条件代码中使用 `__syncthreads()` 但条件在 block 内所有线程上求值不一致）\n- **Divergent thread(s) in warp**：对不支持的 barrier，检测到单个 warp 内线程发散\n- **Invalid arguments**：barrier 指令/原语使用非法参数（如并非所有到达 `__syncwarp()` 的线程都在 mask 参数中声明自己；但 synccheck **不会**检测 mask 中声明的线程未全部到达的情况）\n\n后续行包含函数内偏移、文件名行号（如有）、kernel 名、违规线程和 block 信息。\n\n### 6.4 其他 Synccheck 能力\n- **`cuda::barrier` 支持**：Ampere 及更新 GPU；barrier 数量溢出时警告并可用 `--num-cuda-barriers` 解决\n- **`wgmma` 支持**（Hopper sm_90a）：warpgroup 中每个 warp 应以相同顺序、相同 predicate 执行相同 `wgmma` 指令，且全部线程活跃或全不活跃。违规时报告以 \"Warpgroup MMA sequence error detected\" 开头（而非 \"Barrier error detected\"），每个遇到错误的 warp 报告一次，并退出整个 warpgroup。用 `--check-warpgroup-mma` 启用/禁用\n\n---\n\n## 七、Compute Sanitizer 特性（Features）\n\n### 7.1 非阻塞模式（Nonblocking Mode）\n默认以非阻塞模式启动 kernel，支持并发 kernel 应用的错误报告。`--force-blocking-launches` 强制串行执行（副作用：阻塞模式下只报告 kernel 中第一个出错的线程）。使用 `--force-blocking-launches` 或 `--force-synchronization-limit` 会禁用 CUDA 精简 API 序列化。\n\n### 7.2 栈回溯（Stack Backtraces）\n`--show-backtrace` 生成回溯，通常含主机回溯（至 CUDA driver 调用点）和出错时的设备回溯两部分。\n\n| 输出类型 | 主机回溯 | 设备回溯 |\n|---|---|---|\n| Memory access error | 主机端 kernel launch | 精确设备回溯 |\n| Hardware exception | 主机端 kernel launch | 不精确设备回溯（某些情况下可能无设备回溯） |\n| Malloc/Free error | 主机端 kernel launch | 精确设备回溯 |\n| cudaMalloc allocation leak | cudaMalloc 调用点 | N/A |\n| CUDA API error | CUDA API 调用点 | N/A |\n| Compute Sanitizer internal error | 导致内部错误的调用点 | N/A |\n| Device heap allocation leak | N/A | N/A |\n| Shared memory hazard | 主机端 kernel launch | N/A |\n\n注：OptiX 应用中 OptiX 内部设备函数名显示为 \"NVIDIA Internal\"。\n\n### 7.3 名称反修饰（Name Demangling）\n默认显示完全反修饰名（含 kernel 名和原型信息）；simple 模式只显示名称第一部分；禁用则显示完整修饰名。\n\n### 7.4 动态并行（Dynamic Parallelism）\n支持动态并行。memcheck 支持全局/局部/共享内存访问及全局原子指令的越界和未对齐精确错误报告，硬件异常不精确报告也完全支持。动态并行应用的错误检测需要更多设备内存，内存受限环境中 memcheck 可能因内部内存不足而初始化失败。\n\n### 7.5 错误动作（Error Actions，Table 9）\n\n| 错误类型 | 位置 | 动作 | 备注 |\n|---|---|---|---|\n| Memory access error | Device | 终止 CUDA context | 用户可选择改为终止 kernel |\n| Hardware exception | Device | 终止 CUDA context | 后续该 context 上的调用将失败 |\n| Malloc/Free error | Device | 终止 CUDA context | 用户可选择改为终止 kernel |\n| cudaMalloc allocation leak | Host | 继续应用 | 仅报告错误 |\n| CUDA API error | Host | 继续应用 | 仅报告错误 |\n| Device heap allocation leak | Device | 继续应用 | 仅报告错误 |\n| Shared memory hazard | Device | 继续应用 | 仅报告错误 |\n| Synchronization error | Device | 终止 CUDA context | 用户可选择改为终止 kernel |\n| Compute Sanitizer internal error | Host | 未定义 | 应用行为可能未定义 |\n\n说明：\n- 默认行为：纯主机端错误继续执行；硬件异常销毁 CUDA context；精确错误（内存访问、malloc/free）终止 kernel（不执行后续指令，应用继续在 context 中启动其他 kernel）\n- 可用 `--destroy-on-device-error` 改变 memcheck 检测到的内存访问和 malloc/free 错误的处理\n- racecheck 检测到的 hazard 只报告，不影响执行\n- ⚠️ kernel 提前终止时数据计算可能未完成，依赖该数据的后续 kernel 行为未定义\n\n### 7.6 转义序列（Escape Sequences）\n`--save` 和 `--log-file` 文件名支持：\n- `%%`：字面量 %\n- `%p`：Compute Sanitizer 前端应用的 PID\n- 不匹配过滤器的 GPU 启动 kernel 若调用了可从匹配过滤器的 kernel 到达的设备函数，该设备函数视为被检查（某些工具中可能导致未定义行为）\n\n**过滤器示例**（假设三个 kernel：`gamma`/`delta`/`epsilon`，修饰名分别为 `_Z5gammaPi`/`_Z5deltaPi`/`_Z7epsilonPi`，只想检查 --kernel-name regex='[a-z]{7}' ./app        # 正则：匹配 7 个连续小写字母\n```\n\n### 7.8 Coredump 支持\n- CUDA 11.6 起，`--generate-coredump` 在检测到错误时生成 CUDA coredump，之后目标应用中止\n- Linux：在 cuda-gdb 中用 `target cudacore An example of this is [`torch.mm()`](https://docs.pytorch.org/docs/2.14/generated/torch.mm.html#torch.mm \"torch.mm\") and [`torch.bmm()`](https://docs.pytorch.org/docs/2.14/generated/torch.bmm.html#torch.bmm \"torch.bmm\"). The mathematical libraries that we are calling, and PyTorch internal implementations of operations can produce slightly different results in this case, compared to non-batched computations. In particular, let `A` and `B` be 3D tensors with the dimensions suitable for batched matrix multiplication. Then `(A@B)[0]` (the first element of the batched result) is not guaranteed to be bitwise identical to `A[0]@B[0]` (the matrix product of the first elements of the input batches) even though mathematically it’s an identical computation.\n\nSimilarly, an operation applied to a tensor slice is not guaranteed to produce results that are identical to the slice of the result of the same operation applied to the full tensor. E.g. let `A` be a 2-dimensional tensor. `A.sum(-1)[0]` is not guaranteed to be bitwise equal to `A[:,0].sum()`.\n\n## Extremal values[#](https://docs.pytorch.org/docs/2.14/notes/numerical_accuracy.html#extremal-values \"Link to this heading\")\n\nWhen inputs contain large values such that intermediate results may overflow the range of the used datatype, the end result may overflow too, even though it is representable in the original datatype. E.g.:\n\n```\nimport torch\na = torch.tensor([1e20, 1e20])  # fp32 type by default\na.norm()  # produces tensor(inf)\na.double().norm()  # produces tensor(1.4142e+20, dtype=torch.float64), representable in fp32\n```\n\nDifferent backends may use different algorithms, reduction orders, or accumulation precision for the same operation. A value being representable in a dtype does not guarantee that all intermediate or output values of an operation will remain finite.
