Halving-Doubling：RHD），通信步数少（对数复杂度），时延相对较低，但在非2次幂节点规模下会引入额外的通信量。适合通信域内Server个数是2的整数次幂且pipeline算法不适用的场景，或Server个数不是2的整数次幂但通信数据量较小的场景。\n    - NHR：非均衡的层次环算法（Nonuniform Hierarchical Ring），通信步数少（对数复杂度），时延相对较低。适合通信域内Server个数较多且pipeline算法不适用的场景。\n    - NHR_V1：对应历史版本的NHR算法，通信步数少（根复杂度），时延相对较低，适合通信域内Server数为非2的整数次幂且pipeline算法不适用的场景。NHR_V1算法理论性能低于新版NHR算法，该配置项未来会逐步下线，建议开发者使用NHR算法。\n    - Concatenate），适用于通信域内NPU分布存在多个层次、多个层次间NPU对称或者非对称分布的场景，当通信域内层次间存在带宽收敛时相对收益会更好。\n      \n 是华为集合通信库（HCCL）中用于配置 RDMA 网卡 traffic class（流量类别）的环境变量，在多机 RoCE 组网场景下决定通信报文在 IP 层获得的 QoS 优先级。读完本文，你将掌握该变量的取值范围与默认值、它与 RoCE V2 协议 ToS 域和 DSCP 环境变量，让用户可以为 RDMA 网卡指定统一的 traffic class，从而配合网络设备侧的 QoS 策略，保证通信流量在拥塞场景下获得预期的调度优先级。\n\n在 RoCE V2 协议中，traffic class 不是独立字段，而是直接映射到 IP 报文头的 ToS（Type of Service）域。因此，配置 `HCCL_RDMA_TC` 实际上就是在配置 RDMA 报文 IP 头的 ToS 值。\n\n## 取值范围、默认值与合法性约束\n\n`HCCL_RDMA_TC` 的配置规则如下：\n\n- **取值范围**：`[0, 255]`；\n- **步长约束**：必须配置为 4 的整数倍；\n- **默认值**：`132`。\n\n默认值 132 恰好是 4 的整数倍（132 = 33 × 4），符合合法性要求。该默认值也可以在 HCCL 运行日志中直接观测到，例如 [debug_thinking.md](https://link.gitcode.com/i/9230a754971a16f10dbb3dfe81165b93) 记录的典型日志：\n\n```routeros\n[INFO] HCCL(1595259,alltoall_test):2026-01-06-15:38:29.881.988 [externalinput.cc:1170] [1595259][HCCL_ENV] HCCL_RDMA_TC set by default to [132]\n```\n\n这条日志说明，当用户未显式设置该环境变量时，HCCL 在环境变量解析阶段会按默认值 132 装载，并输出 `[HCCL_ENV]` 级别的记录，便于排查实际生效的配置值。\n\n## 与 RoCE V2 ToS 域的位级对应关系\n\n为什么必须是 4 的整数倍？这与 ToS 域的位结构有关。在 RoCE V2 协议中，`HCCL_RDMA_TC` 的值对应 IP 报文头 ToS 域，共 8 个 bit，其划分如下：\n\n- **bit[0, 1]**：固定为 0（不使用，因此值必须能被 4 整除）；\n- **bit[2, 7]**：DSCP（Differentiated Services Code Point，差分服务代码点）。\n\n因此，**该值除以 4 即为 DSCP 的值**。换算关系可以表述为：\n\n```abnf\nDSCP = HCCL_RDMA_TC / 4\n```\n\nToS 域的位结构示意可参见 [tos.png](https://link.gitcode.com/i/7dd0870ff0dd1a14614d91bcf9df9f57)（来自原文档的示意图）。\n\n实际配置中，DSCP 值需要与网络侧（交换机）的 QoS 策略对应，HCCL 侧只需保证 `HCCL_RDMA_TC` 为 4 的整数倍即可正确换算。\n\n## 配置示例\n\n在启动训练任务前，通过 `export` 设置该环境变量即可：\n\n```\n# 该环境变量配置为25*4 = 100，则DSCP为25\nexport HCCL_RDMA_TC=100\n```\n\n即：当希望 DSCP 为 25 时，`HCCL_RDMA_TC` 应配置为 100。同理，默认值 132 对应的 DSCP 为 33。配置完成后，可通过 HCCL 启动日志中的 `[HCCL_ENV] HCCL_RDMA_TC set to [...]` 记录确认生效值。\n\n## 使用约束：通信域粒度配置优先级更高\n\n需要特别注意的是，`HCCL_RDMA_TC` 是全局环境变量，其生效优先级低于通信域粒度的配置。\n\n若调用 HCCL C 接口初始化具有特定配置的通信域时，通过 `HcclCommConfig` 结构体中的 **`hcclRdmaTrafficClass`** 参数配置了 RDMA 网卡的 traffic class，则**以通信域粒度的配置优先**，环境变量仅作为未显式指定时的兜底默认值。\n\n这一点可以从仓库源码中得到印证：在 HCCL_COMM_TRAFFIC_CLASS_CONFIG_NOT_SET;\ncommConfig.hcclRdmaServiceLevel = HCCL_COMM_SERVICE_LEVEL_CONFIG_NOT_SET;\n```\n\n`HCCL_COMM_TRAFFIC_CLASS_CONFIG_NOT_SET` 表示\"未显式配置\"，此时才回落到环境变量 `HCCL_RDMA_TC` 的取值；而一旦上层通过 `HcclCommConfig.hcclRdmaTrafficClass` 显式赋值，则通信域内的 RDMA 报文 traffic class 以该字段为准。\n\n此外，HCCL 内部创建子通信域（如协商通信域）时也会通过 `HcclCommConfigInit(&subCommConfig)` 初始化配置结构体后再填充字段，例如 [ccu_fallback.cc](https://link.gitcode.com/i/4b9a9789b0bdb9d3e60abe056bd996ac) 中的用法：\n\n```\nHcclCommConfig subCommConfig;\nHcclCommConfigInit(&subCommConfig);\nsubCommConfig.hcclBufferSize = NEGOTIATION_CCL_BUFFER_SIZE;\nsubCommConfig.hcclOpExpansionMode = commConfigOpExpansionAicpu;\n// ...填充 hcclCommName 等字段后调用 HcclCreateSubCommConfig\n```\n\n这说明 `HcclCommConfig` 是通信域级参数的统一载体，`hcclRdmaTrafficClass` 只是其中用于 RDMA QoS 的一个字段，与 `hcclRdmaServiceLevel`（对应 `HCCL_RDMA_SL`）等字段并列。\n\n## 与其他 RDMA 相关环境变量的关系\n\n`HCCL_RDMA_TC` 属于 HCCL 网络相关环境变量之一，在
