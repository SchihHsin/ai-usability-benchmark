Overview / Introductory Note on Checkpointing\n\n> Checkpointing is implemented by rerunning a forward-pass segment for each checkpointed segment during backward propagation. This can cause persistent states like the RNG state to be more advanced than they would without checkpointing. By default, checkpointing includes logic to juggle the RNG state such that checkpointed passes making use of RNG (through dropout for example) have deterministic output as compared to non-checkpointed passes. The logic to stash and restore RNG states can incur a moderate performance hit depending on the runtime of checkpointed operations. If deterministic output compared to non-checkpointed passes is not required, supply `preserve_rng_state=False` to `checkpoint` or `checkpoint_sequential` to omit stashing and restoring the RNG state during each checkpoint.\n\n**RNG / device state details:**\n- The stashing logic saves and restores the RNG state for CPU and one other device type (inferred from Tensor arguments excluding CPU tensors via `_infer_device_type`) to the `run_fn`.\n- If there are multiple devices, device state is saved only for devices of a single device type; the remaining devices are ignored → **may result in incorrect gradients if any checkpointed functions involve randomness.**\n- If CUDA devices are detected, CUDA is prioritized; otherwise the first device encountered is selected.\n- If there are no CPU tensors, the default device type state is saved/restored (default value is `cuda`, settable via `DefaultDeviceType`).\n- **Caveat:** If you move tensors to a new device within `run_fn` (not in the set of [current device + devices of Tensor arguments]), deterministic output vs. non-checkpointed passes is **never guaranteed**.\n\n**Decorator form note:** `checkpoint` may also be called without a
