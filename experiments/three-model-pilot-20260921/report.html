## 一、总体流程（ONNX → ATC → .om）

昇腾上的离线模型转换链路为：**ONNX 模型 →（环境准备）→ atc 命令（--framework=5）→ .om 离线模型 → 板端用 AscendCL 加载推理**。ATC 是 CANN 下的「昇腾张量编译器（Ascend Tensor Compiler）」，把开源框架模型转换成昇腾 AI 处理器支持的 `.om` 格式离线模型，过程中做算子调度优化、权重重排、内存优化（来源：ATC 工具介绍页）。

### 步骤 5：动态 shape 场景（原题若涉及动态 batch/分辨率）

官方 `--input_shape` 参数页的关键约束：

- 原始模型为**静态 shape** 时 `--input_shape` 为**可选**；原始模型为**动态 shape** 时 `--input_shape` **必须**配置。
- 多输入用英文分号分隔、整体加双引号，`input_name` 必须是转换前网络模型中的节点名称：
  ```
  --input_shape="input_0_0:16,32,208,208;input_1_0:16,64,208,208"
  ```
- 动态分档：把对应维度设为 `-1`，并配合 `--dynamic_batch_size` / `--dynamic_image_size` / `--dynamic_dims`：
  ```
  --input_shape="A:-1,32,208,208;B:;C:16,64,208,208"  --dynamic_batch_size="1,2,4"
  ```
- shape 范围（动态 shape）：`--input_shape="input_0_0:1~10,32,208,208"`；**Atlas 200/300/500 推理产品、Atlas 200I/500 A2 推理产品不支持设置 shape 范围**；设 `-1` 表示该维度可用 >=0 任意取值（上限受 host/device 内存限制）。
- 标量输入 shape 为 `[]`，配置为空（如 `"input_name1:;input_name2:16,32,208,208"`），动态分档场景下标量输入必须配置。
- 与 `--insert_op_conf`（AIPP）同用时，AIPP 输出图片宽高须落在 `--input_shape` 范围内。
- 来源：<https://www.hiascend.com/document/detail/zh/canncommercial/800/devaids/devtools/atc/atlasatcparam_16_0016.html>

### 步骤 6：常用可选参数（官方「参数概览」表原文摘录）

官方参数概览表指出：`--framework`、`--model`、`--output`、`--soc_version` 在 `--mode=0/3` 时**必选**；`--input_shape` 为可选。部分与本任务相关项：

- `--input_format`：输入数据格式，默认值 —— **Caffe、MindSpore、ONNX 默认为 NCHW**；TensorFlow 默认为 NHWC。
- `--out_nodes`：指定输出节点。
- `--precision_mode`：精度模式，默认 `force_fp16`；`--precision_mode_v2` 默认 `fp16`（二者不能同时用，官方推荐 `--precision_mode_v2`）。
- `--op_precision_mode`：为不同算子设置不同精度模式（官方注：`--op_select_implmode` 功能已不演进、后续废弃，推荐用 `--op_precision_mode`）。
- `--input_fp16_nodes`：指定输入数据类型为 FP16 的输入节点名称。
- `--insert_op_conf`：插入算子的配置文件（如 aipp 预处理算子）。
- `--log`：日志级别，默认 `null`（不输出）。
- `--check_report`：预检结果保存路径，默认在当前路径生成 `check_result.json`。
- `--mode`：运行模式，默认 0；`--mode=1` 时用 `--om` + `--json` 把原始模型/离线模型转成 json 查看参数，例如：
  ```
  atc --mode=1 --om=$HOME/module/resnet50.onnx --json=$HOME/module/out/resnet50.json --framework=5
  ```
  （注：官方该示例用的是 TensorFlow，命令为 `atc --mode=1 --om=...pb --json=... --framework=3`，`3` 表示 TensorFlow；这里 `--framework=5` 对应 ONNX 是据同一份文档的 `5=ONNX`。）
- 已废弃/待废弃（官方标注）：`--input_shape_range`（已废弃，请勿使用）、`--shape_generalized_build_mode`（后续版本会废弃）。
- 来源：<https://www.hiascend.com/document/detail/zh/canncommercial/800/devaids/devtools/atc/atlasatc_16_0038.html>

## 5. 用 AscendCL 部署 OM

典型推理应用流程：

1. `aclInit` 初始化 AscendCL。
2. 申请运行管理资源：Device、Context、Stream。
3. 加载 OM 模型。
4. 准备输入输出 buffer。
5. 执行模型。
6. 取回输出并后处理。
7. `aclmdlUnload` 卸载模型。
8. 释放运行管理资源。
9. `aclFinalize` 去初始化。

系统管理内存时，从文件加载 OM 可使用：

```cpp
aclmdlLoadFromFile(modelPath, &modelId);
```

```cpp
    &modelMemSize_,
    &modelWeightSize_);

ret = aclrtMalloc(
    &modelMemPtr_,
    modelMemSize_,
    ACL_MEM_MALLOC_HUGE_FIRST);

ret = aclrtMalloc(
    &modelWeightPtr_,
    modelWeightSize_,
    ACL_MEM_MALLOC_HUGE_FIRST);

ret = aclmdlLoadFromFileWithMem(

    &modelId_,
    modelMemPtr_,
```

### 步骤 2：用 `trtexec` 把 ONNX 转成 TensorRT engine

官方 quick-start 的转换命令（逐字）：

```bash

```

官方对参数的说明：
- `--onnx=<model>`：指定输入 ONNX 模型；**若输入为 ONNX 格式，用 `--minShapes`、`--optShapes`、`--maxShapes` 控制输入 shape 范围（含 batch size）**。
- `--saveEngine=<file>`：指定 engine 保存路径（官方以 `--saveEngine=resnet_engine_intro.engine` 为例）。
- `--stronglyTyped`：创建强类型网络（strongly typed network）。

官方 `trtexec` 常用 flag 表（[Command-Line Programs](https://docs.nvidia.com/deeplearning/tensorrt/10.x.x/reference/command-line-programs.html)，TensorRT 10.x 分支）还给出以下与本任务直接相关的选项：

**精度（网络级）**
- `--fp16`、`--bf16`、`--int8`、`--fp8`、`--noTF32`、`--best`：指定网络级精度。
- 官方对 INT8 的警告（原文）：在 INT8 模式下，除非用 `--calib=<file>` 提供 calibration cache 文件，`trtexec` 会为张量设置**随机 dynamic range**，因此结果精度不会符合预期。
- 配合 `--precisionConstraints=none|prefer|obey`，以及 `--layerPrecisions=spec`、`--layerOutputTypes=spec` 做逐层精度控制；spec 示例 `--layerPrecisions=*:fp16,layer_1:fp32`。

**动态 shape**
- `--minShapes=<shapes>`、`--optShapes=<shapes>`、`--maxShapes=<shapes>`：为构建 engine 指定输入 shape 范围；**仅当输入模型为 ONNX 格式时必需**。
- `--shapes=<shapes>`：推理时指定输入 shape；官方说明「若输入模型为 ONNX 格式或 engine 以 explicit batch 维度构建，用 `--shapes` 而不是上面三个」。

**其它常用**
- `--memPoolSize=<pool_spec>`：设置 workspace/tactic 显存池大小（pool 类型含 `workspace`、`dlaSRAM` 等）。
- `--builderOptimizationLevel=N`：构建优化等级。
- `--timingCacheFile=<file>`：加载/保存 timing cache。
- `--profilingVerbosity=[layer_names_only|detailed|none]`。
- `--skipInference`：只构建并保存 engine，不跑推理。
- `--versionCompatible`/`--vc`：版本兼容模式（同 OS 上可在更新版 TensorRT 上运行，仅支持 explicit batch）。
- `--loadEngine=<file>`：从序列化 plan 加载 engine。
- `--dumpProfile`、`--exportProfile=<file>`、`--dumpLayerInfo`、`--exportLayerInfo=<file>`：性能/层信息导出。

**关于 `--stronglyTyped` 与 `--fp16` 是否冲突**：官方两个页面都未说明其互斥或组合关系，**未核实**，不建议仅凭记忆断言。

# PyTorch → ONNX → TensorRT engine 完整部署步骤

## 前置条件

- 已训练好的 PyTorch 模型，导出前调用 `model.eval()`
- CUDA GPU + 已安装 TensorRT（含 `trtexec`，通常在 `/usr/src/tensorrt/bin/trtexec` 或 TensorRT 安装目录的 `samples` 中）
- Python 侧依赖：

```bash
pip install --upgrade onnx onnxscript
```

（PyTorch 官方教程明确：ONNX exporter 使用 `onnx` 和 `onnxscript` 将 PyTorch 算子翻译为 ONNX 算子）

## 第 1 步：PyTorch 导出 ONNX

**方式 A（PyTorch 2.5+ 推荐，dynamo 导出器）**——来源：PyTorch 官方教程

```python
import torch
import torchvision.models as models

# 示例：加载训练好的模型并设为 eval
resnet50 = models.resnet50(weights=models.ResNet50_Weights.DEFAULT).eval()

# dummy 输入（tuple of tensors）
BATCH_SIZE = 32
dummy_input = torch.randn(BATCH_SIZE, 3, 224, 224)

# 推荐：dynamo=True 导出器（基于 torch.export + TorchFX）
onnx_program = torch.onnx.export(resnet50, (dummy_input,), dynamo=True)

# 保存到文件
onnx_program.save("resnet50_pytorch.onnx")

# 校验模型格式正确
import onnx
onnx_model = onnx.load("resnet50_pytorch.onnx")
onnx.checker.check_model(onnx_model)
```

- 不存在 → 进入步骤 2；存在 → 该值即 RAS 硬件故障码，需查《健康管理故障定义》对应版本手册解决（HBM 比特 ECC 故障、icache 数据校验故障、AI Core 超时故障等）。

**步骤 2：排查 NPU 硬件故障**
- 在应用类日志 `log/[run|debug]/plog/plog-*pid*_*.log` 中，检查是否存在 **ECC 相关报错**（含 “ECC”/“ECC error”）或**同一 chipId 上多次报错**。
- 不存在 → 进入步骤 3。
- 存在 → 用 `ascend-dmi` 工具压测 AI Core：
  ```
  ascend-dmi --dg -i aicore -s
  ```
  - 若报错 `GENERAL_WARN` 或 `EMERGENCY_WARN`，表示可能存在 AI Core 问题；
  - 压测异常 → 已知硬件故障，联系技术支持更换硬件；
  - 压测正常 → 在程序中指定其它 Device 再跑，复现则转步骤 3，不复现则可能为硬件故障，联系技术支持。
- `ascend-dmi` 需单独安装，位于 **MindCluster ToolBox** 软件包，与 CANN 的配套关系需另查。

**步骤 3：排查软件故障**
- (a) 在 `log/[run|debug]/plog/plog-*pid*_*.log` 检查是否存在**索引类算子 0x800000 报错**；存在 → 参考“索引类算子索引越界”排查**用户输入数据问题**（典型索引算子：`GatherV2`、`Scatter`、`GatherElements`）；不存在 → 转 (b)。
- (b) 用 **msaicerr 工具**分析准备阶段收集的信息，输出分析报告 `info.txt`，将最小集信息与报告提供给技术支持进一步定位。

# 昇腾训练/推理报 `EZ9999` 的根因定位与排查

## 1. EZ9999 是什么

`EZ9999: Inner Error!` 是昇腾的**内部错误类别错误码**，最典型的出现场景就是 **AI Core Error（AI Core / AI Vector 核执行异常）**：终端日志中含 `there is an aicore error exception` / `there is an aivec error exception`，或 plog 中存在 `Aicore kernel execute failed`（来源：昇腾官方 CANN 8.5.0 商用版文档《AI Core Error问题现象描述》，https://www.hiascend.com/document/detail/zh/canncommercial/850/maintenref/troubleshooting/troubleshooting_0004.html）。

报错本身携带根因线索，解读关键字段：

| 字段 | 用途 |
|---|---|
| `chipId` / `dieId` | 报错芯片，判断是否固定在同一 chip 上报错（固定→偏硬件） |
| `core id` | 报错核，判断是否同一核反复报错 |
| `errcode` / `errorStr` | AI Core Error 的具体错误码与描述（如 `0x10 Illegal instruction, usually caused by unaligned UUB addresses`） |
| `fault kernel_name` | 出错的算子名，直接指向问题算子 |

注意：异步执行时可能多个算子一起报错，**从首报错算子开始排查**。

## 2. 第一步：让报错定位到具体算子（PyTorch 训练/在线推理）

NPU 默认算子异步执行，报错堆栈不是真实调用栈。设置同步模式（来源：hiascend 环境变量参考，如 https://www.hiascend.com/document/detail/zh/canncommercial/80RC22/apiref/envvar/envref_07_0048.html）：

```bash
export ASCEND_LAUNCH_BLOCKING=1   # 强制算子同步执行，打印正确调用栈；有性能下降，仅调试用
```

补充：`=1` 时 task_queue 队列关闭、`TASK_QUEUE_ENABLE` 不生效；支持 Atlas 训练系列与 Atlas A2 系列。

## 3. 官方定位流程（CANN 8.5.0 故障处理 → AI Core Error 专题）

来源：https://www.hiascend.com/document/detail/zh/canncommercial/850/maintenref/troubleshooting/troubleshooting_0005.html

**准备阶段——收集故障信息**（来源：troubleshooting_0006）：

- PyTorch/MindSpore/TensorFlow 的训练、在线推理：**无需复跑业务**，系统默认记录定位信息；离线推理、单算子调用、构图场景需复跑并先设环境变量。
- 需复跑时设置：

```bash
export ASCEND_WORK_PATH=${HOME}/aic_err_info        # 生成 plog、atrace 目录
export ASCEND_PROCESS_LOG_PATH=${HOME}/aic_err_info/plog   # 应用类日志（优先级更高）
```

## EZ9999 是什么

在 CANN 体系中，`EZ9999: Inner Error!` 最常见的形态是 **AI Core / AI Vector 执行异常**（屏幕日志同时含 "there is an aicore error exception" 或 "there is an aivec error exception"，或 plog 中有 "Aicore kernel execute failed"）。它是 Runtime 的兜底错误，本身信息量少，**根因要靠报错日志里的扩展字段 + exception dump + 工具链分析来确定**。

- `chipId / dieId`：报错芯片，判断是否固定卡

- `fault kernel_name`：**出错的算子名**，这是排查的锚点；异步下发时可能有多个算子报错，从**第一个**报错算子开始查

### 0. 为什么默认 traceback 指错行
PyTorch 官方 CUDA semantics 文档 "Asynchronous execution" 一节原文：

> You can force synchronous computation by setting environment variable `CUDA_LAUNCH_BLOCKING=1`. This can be handy when an error occurs on the GPU. 即：CUDA launch 是异步的，assert 在 GPU 上异步触发，报错栈指向的是"下一次同步点"而非真正出错的 op。**任何定位手段的第一步都是让错误在正确的 launch 处同步暴露。**

# 定位 `CUDA error: device-side assert triggered` 的方法

## 1. 为什么栈指向的位置不是出错位置

GPU 操作默认异步执行。PyTorch 官方文档（CUDA semantics notes, "Asynchronous execution" 一节）明确说明：

> You can force synchronous computation by setting environment variable `CUDA_LAUNCH_BLOCKING=1`. This can be handy when an error occurs on the GPU. (With asynchronous execution, such an error isn't reported until after the operation is actually executed, so the stack trace does not show where it was requested.)

来源：https://pytorch.org/docs/stable/notes/cuda.html

因此你看到的 Python 栈（常在 `loss.backward()` 或 `loss_func(...)` 处）只是**第一个与 GPU 同步的调用**，真正触发的 kernel 在更早处。同时，device assert 会污染 CUDA context（sticky error），此后任何 GPU 操作都会跟着报错。

## 2. 定位到出错的那一行

```bash
CUDA_LAUNCH_BLOCKING=1 python train.py
```

加上后，报错栈会指向真正发起出错 kernel 的那一次调用（如 `embedding`、`F.cross_entropy`）。

补充手段：在 CPU 上复现同样的数据路径（去掉 `.cuda()`，或 `CUDA_VISIBLE_DEVICES=""`），CPU 实现通常给出精确错误信息（如 `index out of bounds in dimension 0`），社区文章也验证了"换 CPU 跑一下就能展现完整错误信息"（来源：知乎 https://zhuanlan.zhihu.com/p/341943936）。

## 3. 定位到具体的 kernel

### 方法 A：compute-sanitizer（NVIDIA 官方）

```bash
compute-sanitizer --tool memcheck python train.py
```

四个子工具：`memcheck`（内存错误，默认）、`racecheck`、`initcheck`、`synccheck`。精确错误报告格式（NVIDIA 官方文档示例）：

```
========= Invalid __global__ write of size 4 bytes
=========     at unaligned_kernel():0x160 in memcheck_demo.cu:6
=========     by thread (0,0,0) in block (0,0,0)
```

即报出 **kernel 名、指令偏移、源文件与行号、出错线程/块坐标**（行号需编译时带 `-lineinfo` 或 `-G`）。NVIDIA 文档还注明：sticky 错误会导致后续所有 kernel 启动都报同样错误、无法定位原始出错点——这正是用 sanitizer 的动机。常用定位选项：`--kernel-name`（按 kernel 过滤）、`--launch-skip`（跳过前 N 次启动）、`--generate-coredump`（CUDA 11.6+ 在首个错误处生成 coredump，供 cuda-gdb 用 `target cudacore core.name.nvcudmp` 离线分析）。

来源：https://docs.nvidia.com/compute-sanitizer/ComputeSanitizer/index.html（正文在 memcheck 示例章节处截断，`--launch-timeout` 等选项已取得）

### 方法 B：cuda-gdb

```bash
cuda-gdb python train.py
```

在 device assert 触发处断下，`bt` 查看 kernel 名与 thread/block 坐标；或先用 `compute-sanitizer --generate-coredump` 生成 coredump 再离线分析。

## 4. 最常见的根因（按概率排查）

1. `nn.Embedding` / `gather` / `scatter` / 高级索引越界：索引 ≥ 维度大小或为负。典型：词表 `num_embeddings` 小于 token id 最大值。
2. `CrossEntropyLoss`：target 含 `≥ num_classes` 的值或负值（含 `ignore_index` 误设）。
3. 标签个数与类别数不匹配、loss 变 NaN 后续操作越界（知乎文章亦确认这两类）。
4. 数据本身错误（知乎文章：重新导入数据集后解决）。

快速自检示例：

```python
assert (input_ids >= 0).all() and (input_ids < vocab_size).all()
assert (targets >= 0).all() and (targets < num_classes).all()
```

## 5. 修好后必须重启进程

触发 assert 后 CUDA context 已损坏（sticky error），无法在原进程内"恢复"，修正根因后重新运行。

## 定位 `CUDA error: device-side assert triggered` 的完整方法

### 1. 为什么报错行不可信（机制）

PyTorch GPU 操作默认异步执行：调用只是入队，错误要等 kernel 真正执行后才上报，所以 Python 栈回溯指向的常常是错误发生**之后**的某个 API 调用，而不是出错行。原文依据（PyTorch 官方 CUDA semantics 文档，"Asynchronous execution" 节）：

> "You can force synchronous computation by setting environment variable `CUDA_LAUNCH_BLOCKING=1`. This can be handy when an error occurs on the GPU. (With asynchronous execution, such an error isn't reported until after the operation is actually executed, so the stack trace does not show where it was requested.)"
> — https://pytorch.org/docs/stable/notes/cuda.html

### 2. 第一步：`CUDA_LAUNCH_BLOCKING=1` 同步执行定位出错行

```bash
CUDA_LAUNCH_BLOCKING=1 python your_script.py
```

报错栈会直接指向触发 assert 的算子/代码行。同时看 stderr 中 assert 附带的信息，通常形如：

```
/opt/pytorch/pytorch/aten/src/ATen/native/cuda/IndexKernel.cu:92: Assertion `index out of bounds` failed
```

这给出 CUDA 源文件和行号，可直接判断是哪类越界。

### 3. 第二步：`compute-sanitizer` 定位出错 kernel 与源码行

```bash
compute-sanitizer --tool memcheck python your_script.py
```

官方文档（NVIDIA Compute Sanitizer，memcheck 节）说明：
- memcheck 可精确检测越界/未对齐访存，对 precise 错误能报告 **kernel 名、thread/block 坐标、PC、地址**；若编译带 `-lineinfo` 或 `-G` 还能给出 **源文件:行号**。样例输出：

```
========= Invalid __global__ write of size 4 bytes
=========     at unaligned_kernel():0x160 in memcheck_demo.cu:6
=========     by thread (0,0,0) in block (0,0,0)
```

- 相关选项：`--destroy-on-device-error {context,kernel}`（出错时销毁 context 还是终止 kernel，默认 context）、`--print-limit N`（默认 100 条错误）。
- 对 PyTorch 使用 sanitizer 前需关闭 caching allocator，否则干扰检查（PyTorch 官方文档原文）："To debug memory errors using `cuda-memcheck`, set `PYTORCH_NO_CUDA_MEMORY_CACHING=1`"：

```bash
PYTORCH_NO_CUDA_MEMORY_CACHING=1 compute-sanitizer --tool memcheck python your_script.py
```

**注意（未核实/限制）**：官方 memcheck 文档中未提及 device-side assert 的专门处理；assert 属于硬件异常（hardware exception）类，文档标注其精度为 **Imprecise**——可能拿不到精确 thread/行号，只能拿到 imprecise backtrace。对纯 assert（如 CrossEntropy 标签越界）memcheck 帮助有限，主要靠第 2、4 步。
— https://docs.nvidia.com/compute-sanitizer/ComputeSanitizer/index.html

### 4. 常见根因速查（绝大多数 assert 是索引/标签越界）

- `nn.CrossEntropyLoss`：target 中有 ≥ num_classes 或 < 0（且非 ignore_index）的值 → `Assertion 'srcIndex < srcSelectDimSize' failed`
- `nn.Embedding` / `gather` / 高级索引：index 超出维度范围
- 用 `CUDA_LAUNCH_BLOCKING=1` 定位到行后，打印相关张量的 `min()/max()` 和 shape 核实

### 5. 兜底手段

- **CPU 复现**：`model.cpu()` + 数据搬到 CPU 运行，同样的逻辑错误在 CPU 上会以精确 Python 异常报出（知乎二手源也推荐此法：https://zhuanlan.zhihu.com/p/341943936 ）。
- **`TORCH_USE_CUDA_DSA=1`**：错误提示中会建议设此变量编译以启用 device-side assertions；**注意**：官方 pip/conda 预编译 binary 未启用 DSA，需源码编译 PyTorch 才生效（此点来自报错提示与社区共识，PyTorch 官方 cuda notes 页面未记载，未核实到官方正文）。

## 一、先理解"四层依赖链"的方向

这四者不是简单平级，而是逐层锚定：

1. **驱动（NVIDIA Driver）是最底层**：向上决定"本机最高能跑哪个 CUDA 运行时大版本"。驱动向下兼容——新驱动能跑旧 CUDA，但旧驱动跑不了过新的 CUDA 新特性。
2. **CUDA toolkit / runtime**：官方为每个 toolkit 版本规定了**最低驱动版本**（见 NVIDIA CUDA Release Notes 表）。
3. **PyTorch 是预编译 wheel**：每个 wheel 针对**某一个固定 CUDA 版本**编译（`cu118` / `cu121` / `cu124` / `cu126` / `cu128` / `cu130` / `cu132`）。所以"PyTorch↔CUDA toolkit"的关系不是随便配，而是**用哪个 `--index-url` 装哪个 wheel 就绑定了哪个 CUDA 版本**。
