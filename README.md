# ai-usability-benchmark

一份**可分享的 Claude Code Skill**：衡量「一个会实时检索的 AI 助手，回答某个生态的开发
任务时，知识从哪来、可用性如何，与另一个成熟生态相比差在哪」。

在若干开发者任务上，对两个生态各**真跑一遍检索**（web_search / web_fetch），按统一的
**11 项指标**量化打分、记录每一步、产出可下钻的对照矩阵。

- **默认对照**：受测生态 = CANN（昇腾），基线生态 = CUDA（NVIDIA）。
- **可换任意两个生态**：用户指定（如受测 ROCm、基线 CUDA；受测 TPU/XLA…）时按用户说的来。
  方法本身与具体生态无关。

> 视角是「**会检索的 AI 助手**」，不是「这个栈好不好用」。同一份文档，人能连蒙带猜、能装环境
> 跑；AI 助手只能搜→抓→读正文→拼答案。SPA 页面人能看、AI 抓回来是空的——所以两者相关但不同。

## 安装（作为 Claude Code Skill）

把本目录整个复制进你的 skills 目录，目录名即 skill 名：

```bash
# 个人全局（任何项目可用）
cp -r ai-usability-benchmark ~/.claude/skills/

# 或某个项目内（随仓库分享）
cp -r ai-usability-benchmark <你的项目>/.claude/skills/
```

之后在 Claude Code 里说「测一下 X 生态的 AI 可用性」「跑这些开发任务对比两个栈」即可触发。

## 怎么用（五步）

1. **选任务**：一束有代表性的开发者任务，覆盖「成熟通识 → 前沿深水」。各给代号 A、B、C…
2. **编配对问句**：每任务一对问题，**本质相同、仅换栈**，除工具名外全对齐。**逐字记下原文。**
3. **真跑**：对每个生态 web_search/web_fetch，记下可量化原始观测（轮数、命中排名、抓取形态、
   二手来源类型/平台/日期、并存版本数……）。**绝不编造**——无把握就重搜，拿不到的日期留 `None`。
4. **打分**：把观测填进 `score_template.py` 的 `RAW`（照搬 `EXAMPLE` 字段结构），跑脚本得分。
   这是权威分，任何报告/前端必须与它逐值一致。
5. **呈现**：自定义你的输出（对照矩阵 / 方法论说明 / 改进建议）。用 `--json` 保证 UI 同源。

## 分数是怎么算出来的（以及为什么这么算）

整套打分的目标：把原先靠「主观研判」给的分，换成**可复现的公式**——每个指标一个
`score_N()` 函数，输入是真跑得到的**可量化原始观测**，输出 1–5。下面逐项说清楚
「怎么算」和「为什么这么设计」。所有公式都在 `score_template.py` 里，可逐行核对。

### 价值链：为什么是这 11 个指标，而不是拍一个总分

一条「把知识搬进答案」的链路是有结构的：

```
触达（搜得到 → 抓得到） → 内容质量（够细 → 版本清楚） → 检索成本（摩擦） → 产出（锁版本 / 可复现）
```

而知识有**三个来源渠道**：官方一手 / 二手社区 / 模型自带知识。触达和质量两关，
对每个渠道分别成立 → 于是是「三源 × 两关」网格，拆成 11 个正交指标，而不是一个笼统总分。
这样做的原因：**「搜得到」≠「抓得到」≠「够用」是三件不同的事**（SPA 页面搜得到、
抓回来是空的；抓到了正文也可能只是兜底页）。混成一个分会把这些区别抹平、无法定位短板。

### ①–⑩ 各项怎么算

| 指标 | 怎么算（映射规则） | 为什么这么设计 |
|---|---|---|
| ① 官方可发现性 | 一轮内按官方首条排名分档（rank1→5、前 3→4…）；需二次改写检索才浮出→2 | 排名/轮数是 AI 能否「搜到」官方源的客观代理 |
| ② 官方可抓取性 | 核心页抓取形态映射：`static`5 / `ssr`4 / `partial`4 / `spa`2 / `robots`1 | AI 只能读抓回来的正文；SPA 抓回导航+meta≈废 |
| ③ 官方正文详尽度 | 抓到后看完整度：穷尽+可执行→5、主路径→4…；**SPA/robots 抓不到→「受阻」中性态** | 抓得到≠够用，正交于②；受阻是「没测成」不是「质量低」 |
| ④ 版本清晰度 | 版本无关或≤1 版→5；有支持矩阵→4；双轴可锁→3；≥3 版散乱→2 | 多版本号并存会让 AI 选错版本、给出过时答案 |
| ⑤ 二手丰富度 | 去重二手来源条数分档（≥6→5、≥5→4、≥3→3…） | 官方塌时，二手数量决定有没有兜底 |
| ⑥ 二手可信度/一致性 | `SOURCE_CRED` 类型基准分均值 + 一致性因子 + 时效罚 + 独立性罚，clamp 1–5 | 见下「为什么用锚定表 + 只罚不奖」 |
| ⑦ 模型自带知识 | 自评档 own + 知识截止 gap 罚分（churn 越快罚越多） | 唯一显式自评；用迭代节奏给它一个客观锚 |
| ⑧ 检索成本（反向） | `rounds + 0.5·fetch + 4·fetch_fail`，越小分越高 | 摩擦越大、AI 越可能放弃或出错；抓取失败重罚 |
| ⑨ 版本可锁定性 | exact5 / mostly4 / range3 / none2 | **产出/因变量**——是结果，不进⑪ |
| ⑩ 步骤可复现性 | copyrun5 / params4 / partial3 / skeleton2 | **产出/因变量**——是结果，不进⑪ |

### ⑪ 综合：为什么是「三源噪声-OR」而不是加权平均

```
综合 = K × 版本因子 × 成本因子
K       = 1 − (1−OFF)(1−SEC)(1−OWN)     ← 三渠道任一扛住即可答
OFF     = nm①×nm②×nm③   (官方：发现×抓取×详尽)
SEC     = nm⑤×nm⑥        (二手：数量×可信)
OWN     = nm⑦            (自带知识)
版本因子 = 0.7 + 0.3·nm④   (跨渠道影响，±30%)
成本因子 = 0.9 + 0.1·nm⑧   (±10%)
nm(v)   = v/5；受阻渠道记 0
档位：≥.80 高 / ≥.63 中高 / ≥.45 中 / ≥.24 低 / <.24 很低
```

**为什么 noisy-OR**：回答一个开发问题，**只要三条渠道里有一条扛得住就能答**——
官方文档够好、或二手够厚、或模型自己就会。所以是「或」的逻辑：`K = 1−∏(1−各渠道)`。
加权平均会把「官方满分但二手为零」算成中庸分，**掩盖「其实靠官方一条就能答」的事实**；
也无法表达「三条渠道同时塌才真正致命」这个关键结论。noisy-OR 正好编码了这个直觉。

**为什么 ④⑧ 是全局乘子、不是渠道内项**：版本清晰度和检索成本是**跨渠道**的影响
（版本散乱会同时拖累官方和二手；检索摩擦是整个过程的），所以作用在 K 之外当乘子，
而不是塞进某一个渠道。版本 ±30%（影响大）、成本 ±10%（影响小）。

**为什么 ⑨⑩ 不进 ⑪**：它们是**产出/因变量**——「能不能锁版本、能不能照抄跑」本身
就是前面①–⑧的结果。把结果再加进汇总 = 重复加权，会虚高。它们照打分、用于展示，但不进综合。

### 三个「只罚不奖」修正项：为什么只扣不加

⑥ 的时效（`recency_factor`）、⑥ 的来源独立性（`independence_factor`）、⑦ 的知识截止
gap（`cutoff_gap_factor`）都是**只罚不奖**：

- **够新、平台多样、知识不过时 = 基线，不是加分项**。给加分会把临界格虚高地推过整数档。
- **过时、同平台互抄、迭代太快 = 缺陷，扣分**。
  例：3 条二手全是 CSDN 互抄，「一致性 high」可能只是回声、不是独立互证 → 独立性扣分。

### 为什么用 `SOURCE_CRED` 锚定表给二手打分

二手可信度若逐条拍脑袋会不可复现。改用一张**按来源类型定基准分**的锚定表
（官方镜像 5.0 / 官方仓 5.0 / 官方论坛 4.5 / 云厂商 4.0 / 学术 4.0 / 有声誉问答 3.5 /
个人博客 3.0 / 聚合转载 2.5），取均值再叠一致性/时效/独立性因子。这张表可复核、可争论、可改。

### 为什么基线生态（默认 CUDA）几乎全满分

基线是**相对锚**，不是说它「绝对完美」。成熟生态（静态文档站、厚二手、模型训练覆盖密）
在这套 AI 视角指标下通常接近满分；评测的重点是**受测生态相对这个锚缺在哪**。所以结论
永远是「受测生态在第 N 个指标上比基线低多少、为什么」，而不是孤立的绝对分。

### 一个去重铁律（否则会重复加权）

**官方文档 / 官方代码仓 / 官方论坛属①官方渠道，绝不计入⑤⑥二手。** 否则同一个官方源
会在 OFF 和 SEC 里各算一次，noisy-OR 的渠道独立性被破坏、综合分虚高。

## 两条铁律

1. **绝不编造**：来源标题/URL/日期/版本号无把握 → 重新检索拿到再写。
2. **区分实测/推断/理想化**：能实测就实测；推断必标注；受阻（抓不到正文）记中性态、不打推断分。
