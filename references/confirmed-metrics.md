# 已确认的M2、M3、M8、M10规则

版本：`v2-five-band-2026-09-14`。本版确定以下四项；M1/M4/M5/M6/M7/M9继续保存观测，M11暂不计算。不是整套评分体系已经完成验证。旧版`v2-draft`仍保持全部分值为null，不追溯修改既有运行。

## M2：官方目标正文获取

执行前在协议中确定不同获取目标及其范围，如适配说明、版本配套表；各模型及两个生态采用相同的目标范围。目标对应知识需求，不对应网址数量。同一目标经多个网址读取只计一次，额外调用计入M8。目标不得根据结果临时增删或拆分。

| 分值 | 描述 | 判定 |
|---|---|---|
| 1 | 访问受阻 | 实际访问受限或失败，未取得目标页面内容 |
| 2 | 正文未返回 | 返回标题、导航或框架，未返回目标正文 |
| 3 | 部分正文取得 | 返回部分目标正文，仍有技术性获取缺口 |
| 4 | 经替代路径取得 | 初次遇阻，经重试或替代官方路径取得完整目标正文 |
| 5 | 直接取得正文 | 正常读取取得完整目标正文，无因失败而采取的绕行 |

正常跟随链接或读取多页不自动降为4分。HTML、SSR、Markdown仅是交付属性，不直接决定分数。内容本身不够详细由M3评价。第三方补足不提高官方M2；初次障碍和官方恢复路径分别保存，不能把并行请求虚构为遇阻后换路。本地权限未配置、未尝试、证据不足均标未知，不给1分；猜错网址的404不能直接代表生态目标受阻。

对预定的n个不同目标等权平均：

\[
\bar{x}_{M2}=\frac{1}{n}\sum_{i=1}^{n}s_i,\qquad M2=\lfloor\bar{x}_{M2}+0.5\rfloor.
\]

保留每项目标分、分数和、目标数、原始均值及四舍五入后的五档分；不采用银行家舍入。例：5、5、5、5、1，均值4.2，任务级4分，同时显示“5个目标中1个未取得”。4.5归为5。任务级4分是平均表现，不表示所有目标都取得。

同时报告未取得数（1/2分）、部分取得数（3分）、未知数和已评目标数。只要有目标未知，整体均值和分档保持null，不删除未知项后计算高分。未找到可评价官方资源时保持待定，并由可发现性指标及过程记录说明。

## M3：已取得官方内容对任务要求的支撑

执行前冻结需求ID、说明和importance（core=完成任务必需；supplementary=题目要求的辅助说明）。不能在看到结果后增加辅助要求或改变重要程度。

| 分值 | 判定 |
|---|---|
| 1 | 已取得相关正文，但没有提供可用于完成任务的信息 |
| 2 | 有背景、术语或方向说明，尚不足以完成任何核心环节 |
| 3 | 能支撑部分核心环节，仍缺影响完成任务的关键内容 |
| 4 | 所有核心环节有充分支撑，题目要求的部分辅助说明仍缺失 |
| 5 | 全部预定要求有充分支撑，未发现影响使用的未解决冲突 |

先逐需求保存实际支持及缺口，再给总档。只有背景方向是2；已有具体可用操作/解释、但核心任务仍不完整是3。影响使用的未解决冲突不能宣称相关需求充分支撑。

相关正文全部未取得时标`not_assessable`，score=null，不给1。混合情况分别说明“正文受阻”与“取得后仍缺信息”；总档仅指实际取得内容的支撑，不是整个官网原文质量。检查范围或核心/辅助划分不足以支持确定档位时保持pending，不猜分。

如果预定要求全部是核心要求，则没有4分所对应的辅助缺口，允许跳过该档；不得为了用满五档临时增加任务要求。

## M8：真实获取成本

保存成本明细`(S,F,R,U)`：S=实际搜索调用数；F=实际获取调用数（包括失败）；R=同一获取目标的重试调用数；U=未取得目标正文的获取调用数。R是S/F调用中的子集，U是F的子集，R/U分别报告，不重复加到S/F上。部分正文取得不计入“完全未取得”的U，另留M2状态。

S/F从实际派发事件计算；R/U先根据目标和真实返回判定、列出请求ID，再由程序计数。是否为同一目标的重试不能仅凭相邻调用或同一URL推断。不能判断R/U时为null，不能填0。未派发就被预算/权限阻止的请求不计入S/F/U。日志不完整时同时报告缺口。

时间、token和费用在工具实际暴露时另列；并发耗时之和不是用户等待时间。本版总调用成本为`C=S+F`，不沿用旧版`S+0.5F+4U`。

| M8分值 | C实际调用数 |
|---|---|
| 5 | 1–2 |
| 4 | 3–4 |
| 3 | 5–6 |
| 2 | 7–8 |
| 1 | ≥9 |

C=0不自动给5分，保持待定或不适用。这是每两次调用一档的统一设计约定，不是实测时间等价；所有任务和模型共用阈值，不按本次分布调整。失败和重试按实际调用计一次。比较成本时同时看任务需求支撑和答案完成程度。

## M10：最终操作方案的完整性与一致性

| 分值 | 判定 |
|---|---|
| 1 | 没有形成与任务相关的操作方案 |
| 2 | 只有方向或流程概述，缺少具体操作 |
| 3 | 有具体步骤，但核心链路缺失或接错，需要补充实现、接口或构建环节 |
| 4 | 核心链路已形成，但存在可明确定位、局部修正的实质错误或遗漏 |
| 5 | 在声明的适用条件下，必要步骤完整、前后一致，内容检查未发现实质缺口 |

3与4按修正范围区分：需要重新补齐/选择核心实现或接口，属于3的边界；路线已经完整、仅需明确局部修改，属于4的边界。最终分数应检查整个主方案，不能用某一处错误直接代表整份答案。

合理替换安装路径、硬件型号等环境参数不自动扣分。5分不是实机运行成功；runtime_validation单列not_executed/executed，已执行时保留结果证据。概念解释任务不强求代码，对无操作要求的任务标not_applicable。

按题目要求评主方案。额外方案中的错误单独记录，先说明是否影响主方案或题目要求；不因模型多写内容自动奖励/惩罚。4/5需要说明适用条件；没有足够材料完成全方案核对时保持pending。

## 评价输入与校验

运行metadata选择本版本。需求清单置于`metadata.protocol.requirements`，每项有id、description、importance。用`run_log.py template --run-dir ...`输出评价模板到标准输出；编辑后用evaluate写进原evaluation.json，不增加默认交付文件。

M3/M10的非空score必须为整数1—5，status=scored，并有reason、requirement_refs及可解析的原文evidence_refs。M3还须有official_body_observed=true，冻结需求含core/supplementary分类。逐项requirements判定必须完整并含reason和证据引用。M10须声明scope=main_solution、适用条件和runtime_validation；有额外方案时另列。

M2的预定目标置于`metadata.protocol.acquisition_targets`：每项含id、description、requirement_refs。模板生成对应observation.targets，每项填写score、initial_state、final_official_state、reason、evidence_refs、event_refs；状态代码为not_obtained/partial/obtained/unknown。4分另填recovery_event_refs，且这些事件也列入event_refs。用`scripts.five_band_metrics.aggregate(targets)`计算observation.aggregate，再取band填任务score。

M8 observation保留C对象中的S/F/R/U（兼容原字段名），total_calls存S+F；retry_request_ids/no_body_fetch_request_ids未知时用null。程序核对派发事件、总数与分档；score可待定，正式填分须status=scored和reason。M2/M8也按此状态要求填分。

其他指标和overall仍为null。M2的恢复路径分档与M8成本有部分重合，后续设计M11时须检查重复赋权。此前v2-partial版的无分值规则见[旧版定义](confirmed-metrics-partial-2026-09-14.md)，校验继续兼容，既有实验不自动重算。

脚本验证格式、数值、版本和引用，不会自动读懂网页或证明评价者选择的档位正确。内容判断需按上述边界逐项核验，分歧保留原文与修订理由，不按模型标签调整分数。
